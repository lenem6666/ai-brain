# 架构

## 一句话

把"记忆"从应用层降到数据层：**记忆是文件，应用只是读者**。

## 四层

```
┌─────────────────────────────────────────────────────────┐
│ 接入层  各 AI 客户端的入口文件                             │
│  CLAUDE.md / AGENTS.md / .cursor/rules / GEMINI.md /     │
│  SKILL.md / MCP tools                                    │
├─────────────────────────────────────────────────────────┤
│ 协议层  "读—用—写—同步"的固定动作序列                      │
│  会话开始 brief → 过程中 recall → 结束 add + sync          │
├─────────────────────────────────────────────────────────┤
│ 命令层  brain.py（纯标准库）                              │
│  init / add / recall / brief / compile / sync / doctor   │
├─────────────────────────────────────────────────────────┤
│ 数据层  私有 git 仓库 memory/**.md                        │
│  一条一文件 + YAML frontmatter + 正文                     │
└─────────────────────────────────────────────────────────┘
                    ↕ git pull / push
              其他电脑 / 其他客户端共享同一数据层
```

关键：接入层与命令层**不持有状态**，所有状态都在数据层。
所以删掉任何一个客户端，记忆都不受影响；加一个新客户端，也只是多一个读者。

## 数据模型

一条记忆 = 一个文件。frontmatter 是给机器看的，正文是给模型看的。

| 字段 | 作用 | 示例 |
| --- | --- | --- |
| `id` | 全库唯一，`类型-日期-随机` | `decision-20261020-b15106` |
| `type` | 决定落在哪个目录、进简报的哪一节 | `decision` |
| `scope` | `global` 或项目名，决定生效范围 | `global` |
| `tags` | 检索加权最高的人工标注 | `[架构, 存储]` |
| `created` | ISO 8601 带时区，用于时间衰减 | `2026-10-20T08:50:00+08:00` |
| `source` | `工具@设备`，用于追溯是哪台机器写的 | `claude@win-office` |
| `confidence` | 可选，`high/low`，低置信度不写进简报正文 | `high` |

为什么一条一文件：
- 并发写入落到不同文件，`git pull --rebase` 自动合并，冲突概率 ≈ 0；
- diff 可读，能看清"哪天改了什么想法"；
- 单条可删除、可单独加密、可单独分享。

## 生命周期

```
会话开始
  └─ brain hook start
       ├─ git pull --rebase（25s 超时，失败静默跳过 → 离线可用）
       └─ brain brief → 注入上下文（L0，预算 4000 字符）

会话中
  ├─ 用户提到历史 → brain recall（L1，按需）
  └─ 出现稳定信息 → brain add（立即落库，不等会话结束）

会话结束
  └─ brain hook stop
       ├─ 有变更 → git commit
       └─ git pull --rebase + push
```

没有钩子的客户端，同一序列由入口文件里的协议驱动模型执行；
再加一条每小时的计划任务 `brain sync` 兜底。

## 上下文预算策略

记忆无限，上下文有限。分两级：

| 层级 | 内容 | 体积 | 触发 |
| --- | --- | --- | --- |
| L0 | 身份、全局硬规则、近期决策、条目索引 | ≤ 4000 字符（硬截断） | 每会话一次 |
| L1 | 命中的条目正文 | 每条 ≤ 12 行 | 按关键词 |

排序权重（`recall`）：标题命中 6 分 > tags 命中 4 分 > 正文命中 1.5 分/次（上限 4 次）
> 身份/偏好加成 1.5 > 时间衰减（30 天内最多 +3）。

**为什么不用向量检索**：v0.1 追求"零依赖、离线、任意机器可跑"。
词法打分对"中文 + 关键词式提问"已经够用；记忆量破万再加本地 SQLite + 嵌入层（路线图 v0.3）。

## 同步与冲突

- 唯一写入通道是 `brain add` / `brain sync`，不做后台常驻进程 → 无死锁、无半写状态。
- 推送前先 `pull --rebase --autostash`：本地未提交变更不丢，提交历史保持线性。
- 真冲突（同一条目两端都改）的处理是**自动保留双方**，不让人卡在 rebase 现场：
  1. 从 `REBASE_HEAD` 取出本地版本，另存为新条目（打 `冲突副本` 标签，重算 id）；
  2. `rebase --abort` 后 `reset --soft origin/<branch>`，分支对齐远端、本地改动留在暂存区；
  3. 原条目取远端版本，与副本一起提交、推送。
  结果：双方内容都在、历史保持线性、仓库不停在 rebase 中间态（早期版本会卡死，已修）。
  副本等下次 `brain distill` 时由人裁决合并。
- 同步失败（离线/无权限）不静默：`brain sync` 以退出码 4 报错，本地提交保留，联网重跑即收敛。
- 记忆有变化（`add` 提交、`sync` 拉到新提交）后自动重编译 6 个入口文件——闭环最后一跳，
  新会话不会读到旧快照；`BRAIN_AUTO_REFRESH=0` 可关闭。
- 首次推送自动识别远端无分支，改用 `push -u origin <branch>`。
- 定时任务（`bin/sync-task.cmd`，每小时）自带 git 路径探测：计划任务的 PATH 通常没有 git，
  早期版本因此静默失败，现已兜底到常见安装位置。

## 扩展点

| 想做的事 | 改哪里 |
| --- | --- |
| 加一种记忆类型 | `TYPES` 常量 + 目录 + `cmd_brief` 的分节 |
| 换检索引擎 | 替换 `score()`，接口不变 |
| 加新客户端 | 在 `TARGETS` 加一项入口文件模板 + `adapters/<名字>/README.md` |
| 加新命令 | `build_parser()` 注册 + `cmd_*` 函数 |
| 换同步后端 | 与 `cmd_sync` 解耦：目前是 git，未来可加 `--backend s3` |

## 失败模式

| 故障 | 表现 | 兜底 |
| --- | --- | --- |
| 离线 | `pull/push` 失败 | 本地照常读写并保留提交，`sync` 退出码 4，下次联网自动补推 |
| 同一条目两端改写 | rebase 冲突 | 自动保留双版本（原条目取远端 + `冲突副本`），不卡死、不丢字，distill 时合并 |
| 计划任务里没有 git | 定时同步静默失败 | `sync-task.cmd` 探测 git 路径 + `brain.py` 自身兜底定位，无人值守也能同步 |
| 远端无权限 | `push` 报 403 | `doctor` 会先做 `ls-remote` 探测，提前暴露 |
| git 身份未配置 | `commit` 失败 | `sync` 自动设置仓库级兜底身份 |
| 记忆目录被删 | `require_config` 报错 | 重新 `brain init --repo` 克隆即恢复 |
| 模型不遵守协议 | 漏写记忆 | 每小时定时 `brain sync` + 手动 `add` 补录 |
| 简报超预算 | 尾部被截断 | 截断处明确提示"用 recall 取细节"，不会静默丢 |
| AI 批量删记忆 | `sync` 退出码 3 | 提交前拦截（≥3 条或 ≥30%），`--force` 才放行；已提交内容可从 git 历史恢复 |
| 两端历史无关 | push 被拒 | `init` 会先提交并推送骨架，保证所有设备共享同一个根提交 |
