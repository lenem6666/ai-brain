# 视频对照验证报告

**被验证的主张**：把 AI 个人档案放进 GitHub，实现"跨电脑、跨 AI 共享同一颗大脑"。
**验证对象**：本仓库 ai-brain v0.1。
**验证方式**：`python scripts/validate.py`（8 项自动化检查，全程在临时目录，不碰真实记忆）。

结论先说：**流程成立，但不是视频说的"一步"。** 8/8 检查通过，同时发现并修掉了 3 个会让它在真实使用中崩掉的缺陷。

---

## 一、视频的三个论点，逐条对照

| # | 视频原话（摘要） | 判定 | 证据 |
|---|---|---|---|
| 1 | "AI 自己就能看、直接改，不用折腾接口，不用配复杂插件" | **成立，但有前提** | 检查 6、7 |
| 2 | "支持一键退回，每次改一个标点都有记录，像时光机" | **方向成立，"一键"不成立** | 检查 4、5 |
| 3 | "积累掌握在自己手里，不绑任何一家公司，换系统都还在" | **成立** | 检查 2、8 |
| 4 | "操作只有一步，复制提示词就自动搭好" | **部分成立** | 见第三节 |

### 论点 1：AI 自己就能看、直接改

**成立的部分**：记忆是普通 Markdown，不依赖任何插件协议。实测用 30 行标准库代码
（不调用 `brain.py`）解析 `memory/**/*.md`，得到的条目数与 `brain status` 完全一致——
也就是说，只要能读文件，就能读记忆，语言、运行时、厂商都不限。

**视频漏掉的前提**：客户端必须**能读本地文件或能执行命令**。

- Claude Code / Codex / Cursor / WorkBuddy / Gemini CLI：能，全自动或半自动。
- ChatGPT 网页 / 豆包 / Kimi 网页：**不能**。它们拿不到你磁盘上的文件，
  只能靠粘贴一段快照（`brain compile --target chatgpt`）。视频里"所有 AI 都能共享"
  这句话对网页版不成立，这是产品权限决定的，不是方案能绕过的。

实测同时确认：同一份协议编译成 6 种入口文件后，**正文 sha 完全一致**
（`131e3810085d`），说明"换个 AI 行为就变"不是内容差异导致的，只是加载机制差异。

### 论点 2：一键退回

**成立的部分**：git 确实逐字留痕，能回到任意历史点。实测把一条记忆改坏 → 提交 →
`git checkout HEAD~1`，正文逐字恢复。

**"一键"打了折扣**：实际动作是命令行或 GitHub 网页上的 "Revert"，不是界面上一个按钮；
而且**只有 push 过的历史才在云端**，只提交没推送的，换台电脑看不到。

**更关键的是视频没说清的一件事**：git 只保护"已提交"的内容。
如果 AI 在你还没提交时把 `memory/` 整个删掉，git 历史里根本没有这笔"删除"，
得靠 `git checkout -- .` 从上次提交恢复；如果连仓库都删了，就只能靠远端。

所以本项目补了一层**误删拦截**：`brain sync` 在提交前检查暂存区，
删除条数 ≥3 条或 ≥30% 时直接拒绝（退出码 3），要求人确认后加 `--force`。
实测删 3/4 条（75%）被拦下，`--force` 才放行。

### 论点 3：不绑定任何公司

**成立**。记忆是纯文本，无绝对路径（检查 8 通过），克隆到新机器即可读（检查 2 通过）。
远端可以是 GitHub、自建 Gitea、公司 GitLab，甚至可以不要远端、放进同步盘。

## 三、"操作只有一步"为什么不成立

结构上确实只有**一个仓库 + 一个入口文件**，但落地必须跨过 4 个手工动作：

| 步骤 | 能否让 AI 代劳 | 首次耗时 |
|---|---|---|
| 建 GitHub 私有仓库 | 不能（要你的账号与授权） | 1 分钟 |
| 装 Git / Python | 不能（要管理员权限） | 0–5 分钟 |
| 把 `~/.ai-brain/bin` 加入 PATH | 不能（要改系统环境变量并重开终端） | 1 分钟 |
| 装技能 + 生成入口文件 + 首次 `init` | 能，一条命令 | 1 分钟 |

合计 **约 10 分钟**（第二台机器约 3 分钟）。视频给的是"结构上的一步"，
不是"落地的一步"——这个差别会直接影响第一次使用时的挫败感。

## 四、验证过程中修掉的 3 个真实缺陷

这轮验证的价值不在"通过了"，而在"没通过的那 4 项"。首轮只有 4/8 通过：

| 缺陷 | 现象 | 后果 | 修复 |
|---|---|---|---|
| 初始化不推远端骨架 | 第二台设备 clone 到空库，各自产生无关根提交 | 两台机器的历史**永远合不起来**，跨设备同步直接失效 | `init` 末尾提交并 `push -u` 骨架 |
| `add` 只提交不推送 | 写入后其他设备看不到 | 忘记 `sync` 就丢同步，模型漏执行时尤其明显 | `add` 后尽力推送（15 s 超时，失败静默） |
| 未固定换行符 | Windows `autocrlf=true` 检出成 CRLF | 同一份记忆在不同系统字节不一致，diff 全是噪音 | 记忆仓库写入 `.gitattributes`：`* text=auto eol=lf` |

第四个失败项（版本回退）是换行符问题的连带症状，不单独计。

**误删拦截、LF 固定、首推骨架**这三条，视频完全没提，但缺了任何一条，这套流程在真实多设备使用中都会出问题。

## 五、视频没讲、但决定成败的 5 件事

1. **上下文预算**。记忆会无限长，上下文有限。必须分两级：`brief`（L0，默认 4000 字符，
   硬截断）+ `recall`（L1，按需）。否则记忆越多，AI 越"记不住"。
2. **隐私边界**。仓库必须私有，密钥/证件号/他人隐私一律不写。
   App 自带记忆泄露是泄露给一家公司，这个仓库泄露是泄露全部画像。
3. **客户端钩子差异**。有钩子的（Claude Code）能"关窗即同步"，没钩子的靠协议约束模型，
   再叠一条每小时定时 `sync` 兜底。这不是方案缺陷，是产品差异。
4. **并发冲突**。必须一条记忆一个文件，才能让 `pull --rebase` 自动合并；
   一个大 JSON 文件两端同时写，必然冲突。
5. **记忆会腐烂**。三个月前的偏好可能已经不成立。需要 `brain distill`（路线图 v0.2）
   定期蒸馏去重，否则简报里全是过期规则，比没有记忆更糟。

## 六、最终判定

**可行，且有实测支撑。** 但有三个前提必须先接受：

1. **接受它不是零成本**：首次约 10 分钟，之后每次换机器约 3 分钟；换来的是记忆永久可迁移。
2. **接受它不是全自动**：网页版 AI 只能手动粘贴；命令行 AI 依赖钩子或协议。
3. **接受维护责任在自己身上**：定期蒸馏、定期看 `git log`、不写敏感信息。
   这正是"掌握在自己手里"的代价——视频只说了收益，没说这项成本。

**不建议采用的场景**：只在单一 App 内使用、不换设备、不换模型的人。
这种情况下 App 自带的记忆功能已经够用，自建仓库是过度工程。
